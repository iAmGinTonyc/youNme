# youNme — контекст проекта (для переноса в новый чат)

Вставь этот файл целиком в начало нового чата, чтобы продолжить работу без потери контекста.

## Что это

Telegram Mini App для записи: мастер (бьюти/фото и т.п.) создаёт слоты, модель их
бронирует. Исходная задача — не "календарь", а формализация устной договорённости:
депозит, отмена, время фиксируются как факт, на который можно сослаться, вместо
разрозненных сообщений в переписке, где крайним обычно остаётся мастер.

## Стек

- Фронтенд: Vite + React + TypeScript, статика на GitHub Pages, автодеплой через
  `.github/workflows/deploy-pages.yml` при пуше в `main`.
- Бэкенд: Supabase — Postgres + Edge Functions (Deno). Деплоятся вручную через
  Supabase CLI, НЕ автоматически.
- Бот: обычный Telegram Bot API + вебхук на Edge Function `telegram-webhook`.

## Архитектура

- Один бот, одно приложение. Роль (мастер/модель) определяется исключительно
  присутствием `telegram_id` в таблице `masters` — это не завязано на то, кто владеет
  ботом. Назначение мастеров — вручную, через SQL/REST, self-service нет и не должно
  быть (иначе кто угодно сможет создавать слоты).
- Edge Functions:
  - `verify` — проверяет initData, возвращает роль (master/model).
  - `master` — все действия мастера (list/create_slot/cancel_slot/archive_slot/
    cancel_booking/mark_no_show/mark_completed), один файл, action-роутинг. `list`
    принимает `{archived: boolean}` — false (default) обычный список, true — архив.
  - `client` — все действия модели (list/book_slot/confirm_completed/cancel_booking),
    тоже один файл. `create_invoice` убран вместе со всей Stars-механикой (см. ниже).
  - `telegram-webhook` — принимает апдейты от Telegram: `/start`, `/app`, диплинки
    `/start slot_<id>`. Обработка платежей (`pre_checkout_query`/`successful_payment`)
    убрана вместе со Stars.
  - `send-reminders` — шлёт напоминание модели и мастеру за 3 часа до начала сеанса.
    Не вызывается фронтендом — дёргается по расписанию через pg_cron (см. "Напоминания
    и уведомления" ниже).
- **Критично**: `telegram-webhook` и `send-reminders` обязаны деплоиться с
  `--no-verify-jwt` (их вызывает не наш фронтенд — Telegram и, соответственно, Postgres
  — ни тот, ни другой не шлют Supabase-авторизацию, иначе платформенный gateway режет
  всё 401 ещё до нашего кода). `master` и `client`, наоборот, ДОЛЖНЫ оставаться с
  проверкой JWT (наш фронтенд шлёт anon key). Это уже один раз случайно сломали одной
  командой деплоя на все функции разом — держать раздельно.
- RLS включён на всех таблицах, но без единой policy (anon ничего не может напрямую).
  Все обращения — через Edge Functions с service-role ключом, который Supabase сам
  прокидывает в `SUPABASE_SERVICE_ROLE_KEY`. Авторизация — независимая проверка
  initData (HMAC с бот-токеном) в каждой функции, не полагается на фронтенд.

## Данные (актуальная схема на момент переноса)

```
masters(telegram_id pk, name, created_at)

slots(
  id, master_id, starts_at, duration_minutes, location, note,
  is_paid, price_stars,       -- платная бронь (депозит в звёздах)
  is_private,                 -- личная запись, видна только по диплинку
  archived_at,                -- архивация отменённых слотов (не удаление)
  status: open | booked | cancelled | completed,
  created_at
)

bookings(
  id, slot_id, model_telegram_id, model_name,
  status: confirmed | cancelled_by_model | cancelled_by_master | no_show | completed,
  cancel_reason, cancelled_at,
  telegram_payment_charge_id, -- если бронь оплачена звёздами
  master_confirmed_at, client_confirmed_at, -- двойное подтверждение для возврата депозита
  created_at
)

events(id, slot_id, booking_id, actor_telegram_id, actor_role, action, details, created_at)
-- append-only лог. Никогда не удаляется — это и есть "зафиксированный факт".
```

Миграции лежат в `supabase/migrations/0001..0006`, но **не применяются автоматически**
(нет доступа к DDL через REST/CLI без пароля от Postgres) — только вручную через
Supabase SQL Editor. Если начинается новая миграция — не забыть попросить пользователя
прогнать SQL и сказать явно, что без этого шага фича не заработает.

## Ключевые продуктовые решения

- **Депозит — сейчас просто заявленное число, без реального сбора денег.**
  Изначально депозит собирался через Telegram Stars (`createInvoiceLink` +
  `openInvoice`, автовозврат через `refundStarPayment`), но эта механика была
  полностью убрана по явному решению пользователя — планируется подключить ЮKassa
  для реальной оплаты рублями (см. "Оплата" ниже), а Stars как временное решение не
  устраивало. Сейчас: мастер указывает "Депозит" числом при создании записи
  (необязательное поле, 0/пусто = без депозита), клиент бронирует **сразу**, без
  отдельного шага оплаты — `is_paid`/`price_stars` в схеме остались (не переименованы),
  но это чисто информационные поля ("модель согласилась на такую сумму"), не
  привязанные ни к какому платёжному провайдеру. `telegram_payment_charge_id` у новых
  броней всегда `null`.
- **Факт про депозит логируется независимо от того, был ли реальный платёж** — при
  неявке (`deposit_forfeited`), при отмене клиентом (`deposit_forfeited_client_cancel`),
  при отмене мастером (`deposit_waived_master_cancel`), при завершении обеими сторонами
  (`booking_finalized`). Это события в таблице `events`, не движение денег — сама идея
  "формализованный факт, на который можно сослаться" сохраняется даже без обработки
  платежа.
- **Двойное подтверждение завершения осталось без изменений**: мастер жмёт "Состоялось"
  (`master_confirmed_at`), клиент — "Подтвердить, что всё прошло" (`client_confirmed_at`,
  кнопка появляется только после времени начала записи). Как только оба флага стоят —
  `finalizeIfBothConfirmed` (`supabase/functions/_shared/finalizeBooking.ts`) атомарно
  переводит бронь в `completed`. Гонки исключены той же схемой, что и захват слота:
  условный UPDATE с проверкой текущего статуса в WHERE.
- **Личные (приватные) слоты — сейчас единственный режим.** Раньше был чекбокс у
  мастера "Личная запись (только по ссылке)" с выбором; теперь **все новые записи
  всегда приватные** — чекбокс убран из формы, но код не удалён, а спрятан за флагом
  `PUBLIC_SLOTS_ENABLED = false` (в `app/src/views/MasterView.tsx` и
  `supabase/functions/client/index.ts`), на случай если публичный список когда-нибудь
  понадобится снова. Доступ к записи — только по Telegram-диплинку
  `t.me/<bot>?start=slot_<id>`: бот получает `/start slot_<id>`, проверяет слот, шлёт
  кнопку с `MINI_APP_URL?slot=<id>`; фронтенд читает `?slot=` из URL и явно запрашивает
  этот конкретный слот у `client` функции. После создания записи мастер видит попап
  со ссылкой (копировать / отправить в Telegram через `openTelegramLink`), а не только
  инлайн-строку в списке слотов (та тоже осталась, для повторной отправки).
- **Архивация вместо удаления**: у отменённых слотов свайп влево (как в Telegram,
  Pointer Events — работает и тачем, и мышкой) открывает кнопку "В архив". Архивный
  слот просто перестаёт возвращаться в списке (`archived_at is null` в запросе), но
  строка и история событий остаются в базе — удаление подрывало бы саму идею
  приложения (формализованный факт должен быть неуничтожим).
- **Дизайн**: фиксированная тёмная мраморная палитра с золотом (не подстраивается под
  тему пользователя в Telegram, `setHeaderColor`/`setBackgroundColor` форсируют свои
  цвета). Кастомные календарь/пикер длительности/пикер часов-минут вместо нативных
  `<input>` — у нативных в вебвью Telegram чужеродный вид. Высоты всех полей формы
  унифицированы на 50px.

## Оплата

- **Сейчас реальной оплаты нет вообще.** Telegram Stars как механика полностью убрана
  (см. выше) — ни `createInvoiceLink`/`openInvoice` на фронтенде, ни
  `pre_checkout_query`/`successful_payment` в вебхуке, ни `refundStarPayment` нигде в
  коде не осталось. Депозит — просто число в форме мастера, без сбора денег.
- **План**: подключить приём рублями через обычного платёжного провайдера
  (ЮKassa/CloudPayments/Robokassa, подключается в BotFather → Payments). У Telegram
  разделены правила: цифровые товары обязаны продаваться за Stars, а вот реальные
  услуги/физические товары (запись к мастеру — как раз этот случай) могут идти через
  обычного провайдера с настоящей валютой. Архитектурно это лёгкая надстройка над уже
  готовым `pre_checkout_query`/`successful_payment` — просто другая `currency` и
  `provider_token` вместо пустого. Не реализовано.
- Вывод звёзд в деньги — только через Fragment (fragment.com), кнопка в профиле бота
  → "Manage Bot" → "Balance" → "Withdraw" (доступно только тому аккаунту, что создавал
  бота в BotFather).

## Напоминания и уведомления

- **При бронировании** (`client` функция, `book_slot`) модели сразу приходит сообщение
  от бота: "Вы записаны к мастеру {имя} на {дата}" (`formatRuDateTime` — длинный русский
  формат "31 июля 2026 г., 08:40", не совпадает с сокращённым форматом на фронтенде).
- **За 3 часа до начала** — отдельная Edge Function `send-reminders` шлёт напоминание
  и модели ("Напоминаем о сеансе у мастера {имя} на {дата}"), и мастеру ("Напоминаем о
  сеансе с моделью {имя} на {дата}"). Один раз на бронь — колонка `bookings.reminder_sent_at`
  (миграция 0008) не даёт продублировать.
- **Как это запускается**: pg_cron (расширения `pg_cron`+`pg_net`, включены на проекте)
  дёргает `send-reminders` каждые 10 минут через `net.http_post` — см. миграцию
  `0009_reminder_cron.sql` (в публичном репо секрет заменён на `<CRON_SECRET>`,
  реальное значение стоит только в БД и в Edge Function secret). Посмотреть/поменять
  джобу:
  ```sql
  select * from cron.job where jobname = 'send-reminders';
  select * from cron.job_run_details order by start_time desc limit 5; -- логи запусков
  ```
- Это первый cron-джоб в проекте — раньше вся логика была строго request-driven
  (фронтенд или Telegram-вебхук), теперь есть один процесс, который не привязан ни к
  тому, ни к другому.

## Не сделано / запланировано

- **Клиент предлагает слот мастеру** (обратный сценарий) — договорились: клиент платит
  сразу при отправке предложения (не при принятии мастером), мастер потом
  принимает/отклоняет из своего инбокса; при отклонении — возврат. Дизайн обсуждён,
  код не начат.
- Приём рублями (см. выше).
- Мультитенантность (несколько мастеров на одном боте) — звёзды всё равно упадут в
  одно место (баланс бота), выплаты между мастерами придётся делать вручную, автоматики
  нет и не планировалась.

## Деплой — шпаргалка

Фронтенд — просто `git push` в `main`, GitHub Actions сам соберёт и выложит.

Бэкенд — вручную:
```bash
export SUPABASE_ACCESS_TOKEN=<personal access token пользователя>
supabase functions deploy master client --project-ref dfntlaflldirllhtnjzw
supabase functions deploy telegram-webhook --no-verify-jwt --project-ref dfntlaflldirllhtnjzw
```

Секреты и где что лежит — подробно расписано в `docs/credentials.md` в репозитории
(токен бота, вебхук-секрет, ключи Supabase, где взять personal access token заново
если старый отозвали). Файл специально не содержит реальных значений — публичный
репозиторий.

## Стиль работы с этим пользователем

- Не спрашивать разрешения на каждый мелкий шаг — пользователь ожидает, что решения
  типа "билд → тайпчек → деплой → коммит → пуш" делаются сразу после подтверждения
  фичи, без дополнительных "точно делать?".
- Денежные/политические решения (что происходит со звёздами в разных сценариях) —
  предлагать рекомендацию с обоснованием, но дожидаться явного да/нет перед тем как
  писать код, который двигает реальные деньги.
- Перед тем как объявить фичу готовой — типчек, локальная сборка, визуальная проверка
  через dev-preview (мок), и только потом деплой+коммит. Скриншотить и проверять
  реальные интеракции (клики/свайпы), а не просто верить, что код должен работать.
- Каждая новая миграция требует ручного шага от пользователя (SQL Editor) — всегда
  явно об этом напоминать и давать точный SQL.
