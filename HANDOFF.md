# youNme — контекст проекта (для переноса в новый чат)

Вставь этот файл целиком в начало нового чата, чтобы продолжить работу без потери контекста.

## Что это

Telegram Mini App для записи: мастер (бьюти/фото и т.п.) создаёт слоты, модель их
бронирует. Исходная задача — не "календарь", а формализация устной договорённости:
депозит, отмена, время фиксируются как факт, на который можно сослаться, вместо
разрозненных сообщений в переписке, где крайним обычно остаётся мастер.

## Стек

- Фронтенд: Vite + React + TypeScript, статика на GitHub Pages, автодеплой через
  `.github/workflows/deploy-pages.yml` при пуше в `main`.
- Бэкенд: Supabase — Postgres + Edge Functions (Deno). Деплоятся вручную через
  Supabase CLI, НЕ автоматически.
- Бот: обычный Telegram Bot API + вебхук на Edge Function `telegram-webhook`.

## Архитектура

- Один бот, одно приложение. Роль (мастер/модель) определяется исключительно
  присутствием `telegram_id` в таблице `masters` — это не завязано на то, кто владеет
  ботом. Назначение мастеров — вручную, через SQL/REST, self-service нет и не должно
  быть (иначе кто угодно сможет создавать слоты).
- Edge Functions:
  - `verify` — проверяет initData, возвращает роль (master/model).
  - `master` — все действия мастера (list/create_slot/cancel_slot/archive_slot/
    cancel_booking/mark_no_show/mark_completed), один файл, action-роутинг.
  - `client` — все действия модели (list/book_slot/create_invoice/confirm_completed/
    cancel_booking), тоже один файл.
  - `telegram-webhook` — принимает апдейты от Telegram: `/start`, `/app`, диплинки
    `/start slot_<id>`, `pre_checkout_query`, `successful_payment`.
- **Критично**: `telegram-webhook` обязан деплоиться с `--no-verify-jwt` (Telegram не
  шлёт Supabase-авторизацию, иначе платформенный gateway режет всё 401 ещё до нашего
  кода — пользователь видит "bot did not respond in time"). `master` и `client`,
  наоборот, ДОЛЖНЫ оставаться с проверкой JWT (наш фронтенд шлёт anon key). Это уже
  один раз случайно сломали одной командой деплоя на все три функции — держать
  раздельно.
- RLS включён на всех таблицах, но без единой policy (anon ничего не может напрямую).
  Все обращения — через Edge Functions с service-role ключом, который Supabase сам
  прокидывает в `SUPABASE_SERVICE_ROLE_KEY`. Авторизация — независимая проверка
  initData (HMAC с бот-токеном) в каждой функции, не полагается на фронтенд.

## Данные (актуальная схема на момент переноса)

```
masters(telegram_id pk, name, created_at)

slots(
  id, master_id, starts_at, duration_minutes, location, note,
  is_paid, price_stars,       -- платная бронь (депозит в звёздах)
  is_private,                 -- личная запись, видна только по диплинку
  archived_at,                -- архивация отменённых слотов (не удаление)
  status: open | booked | cancelled | completed,
  created_at
)

bookings(
  id, slot_id, model_telegram_id, model_name,
  status: confirmed | cancelled_by_model | cancelled_by_master | no_show | completed,
  cancel_reason, cancelled_at,
  telegram_payment_charge_id, -- если бронь оплачена звёздами
  master_confirmed_at, client_confirmed_at, -- двойное подтверждение для возврата депозита
  created_at
)

events(id, slot_id, booking_id, actor_telegram_id, actor_role, action, details, created_at)
-- append-only лог. Никогда не удаляется — это и есть "зафиксированный факт".
```

Миграции лежат в `supabase/migrations/0001..0006`, но **не применяются автоматически**
(нет доступа к DDL через REST/CLI без пароля от Postgres) — только вручную через
Supabase SQL Editor. Если начинается новая миграция — не забыть попросить пользователя
прогнать SQL и сказать явно, что без этого шага фича не заработает.

## Ключевые продуктовые решения

- **Платная бронь = возвратный депозит, а не оплата мастеру напрямую.** У Telegram
  Stars нет API для перевода конкретному другому пользователю — есть только списание,
  возврат тому же плательщику (`refundStarPayment`), или ничего. Все звёзды со всех
  платежей падают на баланс **владельца бота** (кто создавал его в BotFather), это
  никак не связано с ролью "мастер" в нашей таблице.
- **Депозит возвращается клиенту только когда ОБЕ стороны подтвердили**, что запись
  состоялась: мастер жмёт "Состоялось" (`master_confirmed_at`), клиент — "Подтвердить,
  что всё прошло" (`client_confirmed_at`, кнопка появляется только после времени
  начала записи). Как только оба флага стоят — `finalizeIfBothConfirmed`
  (`supabase/functions/_shared/finalizeBooking.ts`) атомарно переводит бронь в
  `completed` и дёргает `refundStarPayment`. Гонки исключены той же схемой, что и
  захват слота: условный UPDATE с проверкой текущего статуса в WHERE.
- **Неявка (мастер жмёт "Не пришли")** — депозит остаётся у мастера (у бота), возврата
  нет. Явно залогировано (`deposit_forfeited`) и клиенту приходит сообщение с
  объяснением. Без механизма оспаривания — так решил пользователь явно
  ("без разбирательств").
- **Обычная отмена брони** (не неявка, кнопка "Отменить бронь"):
  - отменяет **мастер** → автоматический возврат депозита клиенту (не его вина).
  - отменяет **клиент** → депозит остаётся у мастера, без возврата ("в этом и смысл
    приложения" — цитата пользователя).
  - Это была настоящая дыра: изначально `cancel_booking` вообще не трогал депозит,
    из-за чего одна реальная тестовая оплата зависла без резолюции. Исправлено и
    задеплоено.
- **Личные (приватные) слоты**: чекбокс у мастера "Личная запись (только по ссылке)".
  Такой слот не попадает в общий список `open_slots` для клиента. Доступ — только по
  Telegram-диплинку `t.me/<bot>?start=slot_<id>`: бот получает `/start slot_<id>`,
  проверяет слот, шлёт кнопку с `MINI_APP_URL?slot=<id>`; фронтенд читает `?slot=`
  из URL и явно запрашивает этот конкретный слот у `client` функции.
- **Архивация вместо удаления**: у отменённых слотов свайп влево (как в Telegram,
  Pointer Events — работает и тачем, и мышкой) открывает кнопку "В архив". Архивный
  слот просто перестаёт возвращаться в списке (`archived_at is null` в запросе), но
  строка и история событий остаются в базе — удаление подрывало бы саму идею
  приложения (формализованный факт должен быть неуничтожим).
- **Дизайн**: фиксированная тёмная мраморная палитра с золотом (не подстраивается под
  тему пользователя в Telegram, `setHeaderColor`/`setBackgroundColor` форсируют свои
  цвета). Кастомные календарь/пикер длительности/пикер часов-минут вместо нативных
  `<input>` — у нативных в вебвью Telegram чужеродный вид. Высоты всех полей формы
  унифицированы на 50px.

## Оплата

- Сейчас — только Telegram Stars (XTR), через `createInvoiceLink` + `openInvoice` +
  `pre_checkout_query`/`successful_payment` в вебхуке.
- **Обсуждали, не сделали**: приём рублями через обычного платёжного провайдера
  (ЮKassa/CloudPayments/Robokassa, подключается в BotFather → Payments). У Telegram
  разделены правила: цифровые товары обязаны продаваться за Stars, а вот реальные
  услуги/физические товары (запись к мастеру — как раз этот случай) могут идти через
  обычного провайдера с настоящей валютой. Архитектурно это лёгкая надстройка над уже
  готовым `pre_checkout_query`/`successful_payment` — просто другая `currency` и
  `provider_token` вместо пустого. Не реализовано.
- Вывод звёзд в деньги — только через Fragment (fragment.com), кнопка в профиле бота
  → "Manage Bot" → "Balance" → "Withdraw" (доступно только тому аккаунту, что создавал
  бота в BotFather).

## Не сделано / запланировано

- **Клиент предлагает слот мастеру** (обратный сценарий) — договорились: клиент платит
  сразу при отправке предложения (не при принятии мастером), мастер потом
  принимает/отклоняет из своего инбокса; при отклонении — возврат. Дизайн обсуждён,
  код не начат.
- Приём рублями (см. выше).
- Мультитенантность (несколько мастеров на одном боте) — звёзды всё равно упадут в
  одно место (баланс бота), выплаты между мастерами придётся делать вручную, автоматики
  нет и не планировалась.

репозиторий.

## Стиль работы с этим пользователем

- Не спрашивать разрешения на каждый мелкий шаг — пользователь ожидает, что решения
  типа "билд → тайпчек → деплой → коммит → пуш" делаются сразу после подтверждения
  фичи, без дополнительных "точно делать?".
- Денежные/политические решения (что происходит со звёздами в разных сценариях) —
  предлагать рекомендацию с обоснованием, но дожидаться явного да/нет перед тем как
  писать код, который двигает реальные деньги.
- Перед тем как объявить фичу готовой — типчек, локальная сборка, визуальная проверка
  через dev-preview (мок), и только потом деплой+коммит. Скриншотить и проверять
  реальные интеракции (клики/свайпы), а не просто верить, что код должен работать.
- Каждая новая миграция требует ручного шага от пользователя (SQL Editor) — всегда
  явно об этом напоминать и давать точный SQL.
